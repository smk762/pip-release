# Assemble the missing PyPI announcement queue

No product or open-source project found on 25 October 2026 tracks a PyPI user's projects, drafts an announcement when one of them updates, and holds that draft for a human to edit and approve before publishing to X, Discord, Telegram, and Patreon. The pieces of that job are mature and separate. PyPI publishes a release feed per project, and the live watchers turn a named package or a dependency file into a raw alert. Social suites that hold an imported post for editing cover ordinary networks such as X and leave Discord, Telegram, and Patreon off the same plan. Patreon's public API can read posts and can notify you after a human publishes one; a Patreon staff reply on 23 April 2026 says posts cannot be created through the API, so the fourth network stays inside Patreon's editor. A tool anyone can run, with public identities in YAML or JSON and secrets in an env file, is a new pipeline: poll each project's feed, write a per-network draft, wait for an edit, then publish, with later networks added as publishers beside the first four. The development case — PyPI user dragonhound_dev, X user dragonhound3, and Patreon AtlasRealms, with Discord and Telegram still unchosen — is configuration for that pipeline, and nothing already on the market is aimed at those identities.

## Watchers follow one package and send a raw alert

PyPI's documented notification surface is RSS, and it is keyed to a project or to the whole index. The feeds page lists newest packages, every new release on the index, and one feed per project at `https://pypi.org/rss/project/<project_name>/releases.xml`, whose items carry the package name, description, version, and a link to the release page ([RSS Feeds, PyPI Docs](https://docs.pypi.org/api/feeds/)). The API introduction tells new integrations to use those feeds, the JSON API, or the Index API, and to leave XML-RPC alone because it is planned for deprecation ([Introduction, PyPI Docs](https://docs.pypi.org/api/)). A maintainer who asked on Discourse for email when the packages they maintain are released was pointed at the per-project feed plus an RSS-to-email service; Warehouse mail about project removal is a different feature ([Discourse thread](https://discuss.python.org/t/relieve-notifications-about-new-pypi-releases/60944)). Whether the public profile HTML for a user such as dragonhound_dev enumerates that account's projects, and whether the older `user_packages` call still answers, was not tested on this pass. The documented substitute is an explicit package list, plus a listing command: `pypi-toolkit package list <username>` is described as listing a user's packages and auditing metadata, and notification is absent from its feature list ([pypi-toolkit](https://pypi.org/project/pypi-toolkit/)).

The hosted watchers follow that same grain. libraries.io puts new releases of a followed package into an on-site newsfeed and can email about new versions of dependencies; its API is free for registered users at **60 requests per minute**, and its user endpoints take a **GitHub login**, returning packages that reference that login's repositories ([libraries.io login](https://libraries.io/login), [libraries.io API](https://libraries.io/api)). The libraries.io repository is AGPL-3.0 and was pushed on **23 October 2026** ([GitHub API](https://api.github.com/repos/librariesio/libraries.io)). NewReleases.io tracks named PyPI projects or an imported `requirements.txt` and delivers email, Slack, Telegram, Discord, Google Chat, Microsoft Teams, Mattermost, Rocket.Chat, Matrix, and webhooks; its pricing page says the service is free and that donations are appreciated, and the pages read describe release notifications with filters, with X and Patreon absent from the integration list ([NewReleases.io PyPI](https://pypi.newreleases.io/), [pricing](https://newreleases.io/pricing)). Anitya at release-monitoring.org registers one upstream project at a time, includes a PyPI backend, and emits Fedora Messaging events such as `anitya.project.version.update.v2`; the software is GPL-2.0 and was pushed on 23 October 2026 ([Anitya user guide](https://anitya.readthedocs.io/en/latest/user-guide.html), [Integrating with Anitya](https://anitya.readthedocs.io/en/latest/integrating-with-anitya.html), [GitHub API](https://api.github.com/repos/fedora-infra/anitya)). Dependabot and Renovate watch versions already declared in a repository and open pull requests a human reviews as code. Renovate checks PyPI by default and can paste upstream release notes into the pull request, and its repository was pushed on **25 October 2026** ([Dependabot version updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-version-updates), [Renovate Python](https://docs.renovatebot.com/python/), [GitHub API](https://api.github.com/repos/renovatebot/renovate)).

Self-hosted package notifiers are the same alert, with a config file in place of an account. `pypi-notifier` 0.1.1 polls a dict of project RSS URLs, stores state in SQLite, and posts to a Discord webhook, sending nothing on the first run; its only listed client is Discord, and the only upload found is **14 December 2024** ([pypi-notifier](https://pypi.org/project/pypi-notifier/)). `release-tracker` takes a PyPI package name, also watches GitHub and GitLab, and notifies through Apprise, whose README names Discord, Slack, Telegram, email, Pushover, and Teams; the MIT repository was created in May 2025 and pushed on 23 October 2026, and it does not describe drafted copy or an approval step ([release-tracker](https://github.com/nikhilbadyal/release-tracker)). `pypi_tools_bot` is a self-hosted Telegram bot whose `/track` command alerts on a new release ([pypi_tools_bot](https://github.com/xnuinside/pypi_tools_bot)). Sheriff-Sap/PYPINotifier last pushed on 22 February 2023, and cenkalti/pypi-notifier, which emailed about `requirements.txt` changes, is archived ([PYPINotifier](https://github.com/Sheriff-Sap/PYPINotifier), [cenkalti/pypi-notifier](https://github.com/cenkalti/pypi-notifier)).

Two 2026 projects sit beside the job and each cover a different half. `herald-post` 0.2.0, uploaded **10 October 2026** with an alpha classifier, can `watch` one RSS or Atom feed and post each new item with the placeholders `{title}`, `{link}`, and `{feed}` to Bluesky, Mastodon, Discord, Slack, Telegram, LinkedIn, and stdout. That watch path posts on later runs with no preview. A separate `preview` then `post` path shows the exact per-channel text of a message the operator already wrote and sends only that draft id. A PyPI project feed is valid RSS, the project description does not mention PyPI, and the channel table omits X and Patreon. A plugin interface is the extension claim ([herald-post](https://pypi.org/project/herald-post/)). OpenAdapt's crier watches GitHub repositories for commits, releases, and merged pull requests, has an LLM write platform-specific drafts, and sends them to a Telegram bot with **Approve, Edit, and Reject**. Approved posts go to Discord, X, and LinkedIn. In that design Telegram is the review inbox. The MIT repository was pushed on **14 October 2026**, has zero stars, and the README does not mention PyPI or Patreon ([openadapt-crier](https://github.com/OpenAdaptAI/openadapt-crier), [GitHub API](https://api.github.com/repos/OpenAdaptAI/openadapt-crier)). Crier is the closest open-source shape for a draft a human can edit, and its source of truth is a GitHub repo list.

## Held drafts cover ordinary networks and stop short of this quartet

SocialBee is the suite whose own help docs describe imported RSS and Zapier items sitting as drafts that stay unpublished until someone marks them approved. Unapproved posts "will not be shared until you set them to Approved," and the approval feature is documented for content imported from RSS, Zapier, CSV, and similar sources ([SocialBee content approval](https://help.socialbee.com/hc/en-us/articles/29979144914711-Content-Approval-for-Your-Posts)). Adding a feed is Content → RSS → Add RSS, the feed is checked **every hour**, and the Approved toggle can be switched to Drafts so items wait ([SocialBee RSS](https://help.socialbee.com/hc/en-us/articles/29979191413783-How-Do-I-Add-RSS-Feeds-in-SocialBee)). Zapier's only SocialBee action, Create Post, has an "Import as Approved or Draft" field ([SocialBee Zapier](https://help.socialbee.com/hc/en-us/articles/29979077611287-Integrations-How-Can-I-Use-the-Zapier-Integration)). Approvals are absent from Bootstrap at $29/month and present on **Accelerate at $49/month** ([SocialBee](https://socialbee.com/)). The publish list on that page is Facebook, Instagram, X, LinkedIn, Pinterest, TikTok, YouTube, Threads, Bluesky, and Google Business Profile. A PyPI project feed can be pasted in as generic RSS, which makes SocialBee the closest off-the-shelf version of "a release becomes a draft a person edits." Discord, Telegram, and Patreon are absent from that list, and no SocialBee page reviewed mentions PyPI.

The products that list X together with Discord and Telegram document a weaker hold, or a draft flag with no reviewer screen. Postiz's platform table includes X, Discord (**1,980 characters**, OAuth), and Telegram (**4,096 characters**, a bot in a group or channel), and omits Patreon ([Postiz platforms](https://docs.postiz.com/general/platforms/overview)). Cloud Team is **$39/month** and is where RSS auto-posting and team members start; the docs define RSS auto-posting as turning feeds into scheduled posts ([Postiz plans](https://docs.postiz.com/cloud/plans)). A comparison sentence says a person approves agent output in a visual calendar, and the plans and webhook pages do not describe a status that blocks publishing ([Postiz vs Mixpost](https://postiz.com/compare/postiz/mixpost)). OmniSocials lists the same three networks, posts Telegram and Discord through a bot or an incoming webhook, and names webhook events `post.approved` and `post.rejected`; the fetched API page does not describe a reviewer screen, and Patreon is absent ([OmniSocials API](https://omnisocials.com/api)). Breakreach, checked against its publishing code on 12 October 2026, includes X, Telegram channel posts, and Discord channel webhooks, and `POST /v1/posts` can save a draft; the page does not describe a reviewer role or Patreon ([Breakreach posting API](https://www.breakreach.com/developers/posting-api)).

Publer and Buffer each have a real queue and a different pair of networks. Publer's help center, updated 23 September 2026, lists Telegram groups and channels and lists X only on a paid subscription because of X's API cost; Discord and Patreon are absent ([Publer supported networks](https://publer.com/help/en/article/what-social-networks-are-supported-npoun1/)). Business, described in the help center as starting at **$10 per social account per month**, adds approval workflows and API access. Professional, starting at $5, includes unlimited RSS automations that auto-post or auto-schedule and does not list approval ([Publer plan comparison](https://publer.com/help/en/article/professional-vs-business-vs-enterprise-plans-1sge3f7/)). Native RSS offers Auto-post, Auto-schedule, or No Action, and No Action is a library a person picks from ([Publer RSS](https://publer.com/help/en/article/rss-feeds-in-publer-tmy7cj/)). Zapier can create a Publer post as publish-now, scheduled, or draft, and can observe "Post Pending Approval" ([Publer Zapier](https://publer.com/help/en/article/how-to-connect-to-zapier-and-automate-your-workflows-18mun8n/)). Buffer's Team plan, shown at **$10 per channel per month** on annual billing, is the tier with content approval workflows ([Buffer pricing](https://buffer.com/pricing)). A member whose permission is Needs Approval can create drafts and cannot publish; posts that such a member creates through the Buffer API stay in Drafts until an owner approves, edits, and queues them ([Buffer draft approval](https://support.buffer.com/en-us/articles/requesting-approval-and-approving-draft-posts-57li7M8tDA)). Buffer's channel table includes X and omits Discord, Telegram, and Patreon, and Buffer has no native RSS auto-post. The documented RSS path is a Zapier "Add to Queue" ([Connecting channels to Buffer](https://support.buffer.com/en-us/articles/connecting-your-channels-to-buffer-HvWLgAJvL9), [Buffer and Zapier](https://support.buffer.com/en-us/articles/using-zapier-with-buffer-EapRng2lI7)).

Other approval products are real, and they review posts a person already composed. Mixpost Pro is **$299 once**, includes an approval flow whose API moves a `needs_approval` post to `scheduled`, and Discord, Telegram, and Patreon are absent from its official network list. Lite is the open-source edition and omits the approval flow ([Mixpost pricing](https://mixpost.app/pricing), [Approve a post](https://docs.mixpost.app/api/reference/approve-post)). Hootsuite Advanced is **$399 per user per month** on annual billing and is the tier described as review-and-approve ([Hootsuite pricing](https://www.hootsuite.com/pricing)). Loomly lists approval workflows on Starter, $65/month or $49/month billed yearly ([Loomly pricing](https://www.loomly.com/pricing)). Later's Growth plan includes approvals, and its own help says **scheduled posts publish at their scheduled time regardless of approval status**, so the hold is a draft or a permission flag ([Later approvals](https://help.later.com/hc/en-us/articles/40954654500375-Team-Collaboration-and-Content-Approvals)). Sprinklr publishes only after approval, including tiered paths ([Sprinklr approval](https://www.sprinklr.com/help/articles/approval-workflows/how-to-set-the-approval-workflows-while-publishing/6454897b0d27fc559bbeb45e)). None of these vendor pages, on the pricing, approval, RSS, and platform documents reviewed, mention PyPI or changelog announcements as a product feature. An auto-poster article dated 15 October 2026 tells the reader to point a poster at a PyPI project feed and describes automatic posting; the destinations named in its opening answer are Mastodon, Bluesky, Discord, Matrix, and team chat ([postrss.com](https://postrss.com/pypi-release-rss-feed-auto-post/)).

Vendor tools aimed at GitHub releases claim the hold and still miss this quartet. SocialHandoff's site says a GitHub Action or signed webhook creates per-network drafts from a published release and that the action publishes only after a person approves in an inbox; the named networks are X, Bluesky, LinkedIn, and Mastodon ([SocialHandoff release announcements](https://socialhandoff.com/use-cases/release-announcements/), [GitHub releases help](https://socialhandoff.com/help/github-releases/)). Ship 2 Post's site says a GitHub App drafts channel-native copy and holds it for one approval, and its integration list includes Discord and X among a wide set, with Telegram and Patreon absent and an invitation to request unlisted destinations ([Ship 2 Post](https://s2p.dev/auto-post-github-releases-to-social-media), [integrations](https://s2p.dev/integrations)). Octopost's GitHub-release example posts to `platforms: ["twitter"]` with `queueStatus: "pending"` so the item waits, or `published: true` to skip review ([Octopost](https://octopost.ink/cross-post-github-release)). No source repository was found for these three, so the behavior is vendor copy. They start from a GitHub `release` event. PyPI's feeds page documents RSS and does not describe an outbound webhook ([RSS Feeds, PyPI Docs](https://docs.pypi.org/api/feeds/)).

## Chat, X, and Patreon each publish on their own terms

The maintained open-source GitHub Actions post a string the workflow already has, on the event the workflow names, usually `release: published`. `cbrgm/mastodon-github-action` posts a caller-supplied message, is Apache-2.0, and was pushed on **22 October 2026** ([mastodon-github-action](https://github.com/cbrgm/mastodon-github-action)). `myConsciousness/bluesky-post` posts a `text` input, is BSD-3-Clause, and was pushed on **16 August 2026**; the Marketplace page documents v6 ([Send Bluesky Post](https://github.com/marketplace/actions/send-bluesky-post)). Discord release actions such as `SethCohen/github-releases-to-discord` clean a GitHub release body into an embed and send it to a webhook ([Github Releases To Discord](https://github.com/marketplace/actions/github-releases-to-discord)). `tyagdit/release-telegram-action` sends the release body to a Telegram channel after cleanup ([Release Telegram Action](https://github.com/marketplace/actions/release-telegram-action)). `multi-release-notify` can build a title such as `owner/repo updated to v1.2.0` from commit subjects and format it per channel, and it sends automatically when a notification URL is set ([multi-release-notify](https://github.com/sinspired/multi-release-notify)). Those READMEs include no draft, edit, or approve input. Release Drafter and `softprops/action-gh-release`, both pushed on **24 October 2026**, draft or publish the GitHub release itself ([release-drafter](https://github.com/release-drafter/release-drafter/), [action-gh-release](https://github.com/softprops/action-gh-release)). twitter-together publishes `*.tweet` files when they reach the default branch and previews them on a pull request. That review is of a tweet a person already wrote, the repository was last pushed on 16 October 2024, and it is wired to file pushes on the default branch ([twitter-together/action](https://github.com/twitter-together/action)). One repository's own workflow, orallexa, calls an LLM for X, Bluesky, and Mastodon and commits drafts under `queue/pending/` for a maintainer to move to `queue/approved/`. That queue belongs to that repository's marketing agent ([orallexa release-announce.yml](https://github.com/alex-jb/orallexa-marketing-agent/blob/main/.github/workflows/release-announce.yml)).

X posting in 2026 is a metered create call, and the approval queue sits entirely outside X. Direct fetches of docs.x.com returned **HTTP 403** on 25 October 2026, so the rates below come from a documentation mirror that reproduces the docs.x.com changelog header, with the same figures repeated by OpenTweet and Postzen. Effective **20 April 2026**, that changelog sets `POST /2/tweets` at **$0.015 per post** and a post that contains a URL at **$0.20** ([X API changelog mirror](https://x-preview.mintlify.app/changelog), [pricing mirror](https://x-preview.mintlify.app/x-api/getting-started/pricing)). A release announcement that includes the PyPI URL is the $0.20 case on that schedule. The same mirror says pay-per-use has no subscription, credits are bought in the developer console, and official Python and TypeScript SDKs exist. An older pilot entry and an undated snapshot still show content creation near $0.01, so the live console is the rate card that matters. The widely copied v1.1 actions are stale: `ethomson/send-tweet-action` last pushed on 4 March 2023, and a May 2025 comment on the still-open issue #28 says it no longer works because the previous API is unsupported ([send-tweet-action](https://github.com/ethomson/send-tweet-action), [Issue #28](https://github.com/ethomson/send-tweet-action/issues/28)). `snow-actions/tweet` last pushed on 21 April 2023 and its Marketplace page still says to generate v1.1 tokens ([snow-actions/tweet](https://github.com/snow-actions/tweet), [Tweet action](https://github.com/marketplace/actions/tweet-action)). `nearform-actions/github-action-notify-twitter` was pushed on **16 October 2026** with no license set in the API. Commenters in 2024 disagreed about whether it returned HTTP 403, and a 2026 success report was not found ([repository metadata](https://github.com/nearform-actions/github-action-notify-twitter)). n8n's X node documents create, reply, delete, search, like, and retweet, with no draft state, and it still documents likes after the April 2026 changelog says likes left self-serve tiers ([n8n X node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.twitter/)). IFTTT's "post a new tweet" action is an immediate send ([IFTTT X](https://ifttt.com/twitter)).

Discord and Telegram publish as soon as the send is called, so a human gate has to live in the caller. An incoming webhook is an HTTP endpoint for one channel. Executing it is `POST /webhooks/{webhook.id}/{webhook.token}` with content, embeds, and files, and the parameter list has no pending or draft field. `wait` waits for the server to confirm the send. Discord also offers a GitHub-compatible execute URL that renders a GitHub `release` event into the channel ([Discord webhook resource](https://docs.discord.com/developers/resources/webhook)). A server can have at most **50 integrations** ([Server Integrations](https://support.discord.com/hc/en-us/articles/360045093012-Server-Integrations-Page)). Webhook message content is limited to **2,000 characters**, which is why Postiz's 1,980-character Discord figure sits just under the platform cap ([Discord webhook resource](https://docs.discord.com/developers/resources/webhook)). Telegram's `sendMessage` returns the sent message, takes `chat_id` and `text` of **1 to 4,096 characters**, and accepts a channel `@username`. The documented parameter list has no channel-draft flag and no moderator-approval flag, and `suggested_post_parameters` applies to direct-message chats ([sendMessage](https://core.telegram.org/bots/api/methods/sendmessage.md)). A bot posts to a channel only after it is added as an administrator with permission to post. n8n's Discord node can "Send and Wait for Response" with an Approval button, which pauses the workflow until a person clicks; the announcement itself is a later step ([n8n Discord node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.discord/)). The official n8n Telegram node page lists "Send Message" and does not list a wait operation ([n8n Telegram node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.telegram)). Community n8n templates use a Telegram chat as the review room and publish to X after approval, which is a workflow wrapped around immediate-send APIs ([n8n template 11121](https://n8n.io/workflows/11121-auto-create-and-publish-x-threads-twitter-with-gpt-via-telegram-and-approval-loop/)). Octopost states that an X post must fit **280 characters** and that a link counts as 23. That accounting is the vendor's, because the first-party X docs were not readable on this pass ([Octopost](https://octopost.ink/cross-post-github-release)). One changelog cannot be pasted unchanged into Discord, Telegram, and X.

Patreon already has the edit-and-schedule step, and it lives in Patreon's editor. Help Center articles updated in 2026 describe a required title, optional attachments, a "Set publish date" toggle, unscheduling back to a draft, and early access for paid audiences ([Scheduled posts](https://support.patreon.com/hc/en-us/articles/360031956632-Scheduled-posts), [Posting to your Patreon](https://support.patreon.com/hc/en-us/articles/115004048046-Posting-to-your-Patreon)). Public API v2 documents `GET` for a campaign's posts and for one post, `POST` for livestreams and for webhooks, and webhook events `posts:publish`, `posts:update`, and `posts:delete`. It does not document a POST that creates a campaign post. The reference says public API v1 retires on **7 October 2026**, with a possible extension through 20 January 2027 for clients who requested one by that date ([Patreon API reference](https://docs.patreon.com/)). On the developers forum, staff account @noertap wrote on **23 April 2026**: "Currently there is no way to create posts through the api" ([Creating Posts Via API](https://www.patreondevelopers.com/t/creating-posts-via-api/11305)). Zapier's Patreon operations are membership events ([Zapier Patreon](https://zapier.com/apps/patreon/integrations)). Buffer's and Publer's network lists omit Patreon. `Shynixn/PatreonPostApi` states that the official API has no create-post action and that Selenium-style automation is typically blocked by Cloudflare. Its workaround is a Chrome extension in a browser where the creator is already logged in, and the README tells the operator to leave Auto-submit and Background fetch disabled so the filled composer waits for a human to click Post ([PatreonPostApi](https://github.com/Shynixn/PatreonPostApi)). For AtlasRealms, the supported path is a person in that creator's editor. An API client that creates the post has nothing to call in the documented public API.

## A general tool still has to own the poller, the editor, and four publishers

The requirement that anyone can run the tool, with public identities in YAML or JSON and secrets in an env file, rules out one-repository workflows as the product. WeakAuras and gopodder fan one GitHub release out to several immediate posters, and each file is that project's CI ([WeakAuras release notifications](https://github.com/WeakAuras/WeakAuras2/blob/ccfbf553/.github/workflows/release_notifications.yml), [gopodder notify.yml](https://github.com/cbrgm/gopodder/blob/main/.github/workflows/notify.yml)). A stranger cannot point those files at dragonhound_dev by editing a public identity record. Hosted suites are usable by anyone with an account, and each one drops at least two of the four destinations or drops the hold. Crier and herald are installable by anyone and still need a PyPI-user front end, an editor that covers all four texts, and a Patreon handoff.

| Closest existing piece | Where a release enters | What a human can change | X | Discord | Telegram | Patreon |
| --- | --- | --- | --- | --- | --- | --- |
| SocialBee Accelerate ($49/month) | Any RSS feed, polled hourly, or a Zapier create | Imported items can be forced to stay drafts until approved | Yes | Absent from its list | Absent from its list | Absent from its list |
| Publer Business (help-center figure: $10 per account per month) | RSS auto-posts or auto-schedules; Zapier can save a draft | Business approval workflow; native RSS does not enter that queue by itself | Paid plans | Absent from its list | Yes | Absent from its list |
| Postiz Team ($39/month) | RSS becomes scheduled posts | Calendar wording only; no blocking status in the plans or webhook docs | Yes | Yes (1,980 characters) | Yes (4,096 characters) | Absent from its list |
| openadapt-crier (MIT, self-hosted) | GitHub commits, releases, and merged pull requests | Telegram Approve, Edit, and Reject, then publish | Yes | Yes | Review inbox | Absent from its README |
| n8n, assembled by the operator | A webhook or a poll the workflow supplies | Discord Approval button; editing the body is a further step | Create-tweet node, immediate when it runs | Send, or send-and-wait | Send Message | No create-post node in the pages reviewed |

The configuration that matches the requirement is small and public. A record names the PyPI user dragonhound_dev (`https://pypi.org/user/dragonhound_dev/`), the X account dragonhound3 (`https://x.com/dragonhound3`), and the Patreon campaign AtlasRealms (`https://www.patreon.com/c/AtlasRealms`), and it leaves Discord and Telegram empty until a channel and a chat are chosen. Webhook URLs, bot tokens, and X credentials belong in the env file. That split is ordinary for GitHub Actions secrets, and no PyPI watcher ships it as the product.

What that product still has to contain is the join. Username discovery is the untested edge: the feeds page has no user URL, libraries.io's user routes are GitHub logins, and the listing CLI does not watch. The sound first cut is an **explicit project list** in the public file, refreshed by a listing command, with each project polled at `releases.xml`. The first run should record current items and send nothing, which is the behavior already documented for herald's watch path and for `pypi-notifier`. Each new item then becomes four drafts. The RSS fields are a name, a description, a version, and a link, and the PyPI watchers documented here forward that alert as-is. Templates are the verified mechanism. An LLM draft is demonstrated by crier for GitHub events and by orallexa for one repository, and either can sit behind the same hold. The hold has to be an editable artifact. n8n's Approval button approves or rejects. Buffer, Publer, SocialBee, herald's preview id, crier's Telegram Edit action, and orallexa's pending folder are the patterns that change the text before send. After approval, Discord is a webhook POST, Telegram is `sendMessage` from an admin bot, and X is `POST /2/tweets` budgeted at the URL rate on the April 2026 mirror. Patreon is a paste card, or an unsupported browser fill, and then the creator's own Schedule button. Later platforms have a clear order. Mastodon and Bluesky already have actions pushed in 2026, and LinkedIn and Slack already appear as ordinary destinations on Buffer, Ship 2 Post, and sample release workflows. Herald's plugin interface is the open-source extension claim attached to a multi-channel poster, and that poster watches one feed the operator names.

n8n is the closest verified kit for assembling the job in a workflow runner: a webhook or a poll, a Discord approval button, then Telegram and X sends ([n8n Discord node](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.discord/)). Using it still means writing that workflow, trimming each draft to the channel cap, paying X per approved URL, and opening Patreon by hand. SocialBee Accelerate is the closest verified product when the priority is "RSS in, a human edits, several networks out" and the chat networks can wait. Postiz, Breakreach, or OmniSocials are the closest verified products when the priority is X, Discord, and Telegram behind one API and the hold is a saved draft the operator still has to enforce. None of those choices tracks a PyPI user, and none of them publish to Patreon.

## Conclusion

The build worth doing is an identity layer in front of publishers that already exist, because a subscription or a GitHub Action answers a neighboring question and still leaves PyPI-user tracking and Patreon outside the product. For dragonhound_dev, the first useful version stores that user's projects in the public file, treats dragonhound3 and AtlasRealms as named destinations, and leaves Discord and Telegram blank until those channels are chosen. Each approved X post that carries the release link should be costed at the **$0.20** URL rate from the April 2026 mirror until the live console says otherwise. The publisher interface should keep Patreon as a handoff for as long as the v2 reference and the 23 April 2026 staff reply stand, and it should add Mastodon and Bluesky first, because those clients were still being pushed in 2026 while the v1.1 tweet actions were not.
